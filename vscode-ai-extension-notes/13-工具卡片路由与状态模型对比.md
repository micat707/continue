# 工具卡片路由与状态模型对比

> [!abstract] 一句话
> Kiro 用「**按功能域状态切片 + toolCallId 寻址**」渲染工具卡片，运行期 O(1) 增量更新、不抖；Continue 用「**toolCallState 挂 history + 按工具名 switch**」，加载期天然完整、但流式 chunk 会 clone 整棵 history。我们已用「history 持久化 + runId 切片做高频输出」的混合模式拿到两者大部分收益，**是否全盘改造成 Kiro 模式暂缓**。

> [!info] 数据来源
> Kiro bundle：`D:\soft\Kiro\resources\app\extensions\kiro.kiro-agent\packages\kiro-ui-agent-chat\dist\assets\mermaid-*.js`（UI store）、`HostCapabilitiesProvider-*.js`（事件 dispatcher）。
> Continue 改造实测：`My-Agent-editor/continue/` 的 DeepAgent 结构化改造（2026-11）。

---

## 1. 两种模式的核心差异

### Kiro：按「功能域」切片，按 id 寻址

Kiro 的 UI store **没有** `switch(toolName)` 路由表，而是按交互模式划分独立切片：

```js
activeUserInput: null,        // 当前活跃的用户输入卡
userInputAnswers: {},         // 按 requestId 存答案
streamedShellOutput: {},      // 按 runId 存流式 shell 输出
executionChangedFiles: [],    // 执行产生的文件变更
activeElicitation: null,
permissionRequestQueue: [],   // 审批队列（按 toolCallId 去重）
```

action 全部按 id 寻址、原地更新：

```js
setUserInputAnswer:  (id, answer) => ({ userInputAnswers: { ...state, [id]: answer } })
appendShellChunk:    (runId, chunk) => ({ streamedShellOutput[runId] += chunk })
clearShellChunk:     (runId) => ...
enqueuePermissionRequest: 按 toolCallId 找 index，已存在则更新而非重复入队
```

事件分发：`HostCapabilitiesProvider` 里用 `ao` / `Xa` 两级 Map 做 `sessionId → event key → listener` 路由，按 session 投递，不串会话。

### Continue：按「工具名」switch，状态挂 history

`gui/src/pages/gui/ToolCallDiv/FunctionSpecificToolCallDiv.tsx`：

```ts
switch (toolCall.function?.name) {
  case BuiltInToolNames.CreateNewFile:    → <CreateFile />
  case BuiltInToolNames.ReadFile:         → <ReadFile />
  case BuiltInToolNames.EditExistingFile: → <EditFile />
  case BuiltInToolNames.RunTerminalCommand: → <RunTerminalCommand />
  case "user_input":                      → <UserInputCard />
  default:                                → null
}
```

状态全在 `sessionSlice.history[i].toolCallState`（`toolCallId` + `status` + `output` + `parsedArgs`），高频流式输出靠独立 `executeProgressStore[runId]`（半只脚已踏进切片模式）。

> [!note] 澄清：工具名统一 ≠ 路由表统一
> switch 是「不同工具用不同 UI 组件」的路由，和工具定义存哪里无关。Kiro 卡片按**交互模式**分类（输入 / 流式输出 / 审批 / 文件变更），`fs_write` 和 `str_replace` 共用「文件变更」切片，所以不需要各写一个 case。

## 2. 性能对比

| 场景            | Kiro 切片模式                                                                                           | Continue history 模式                                                             | 更快                   |
| --------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------- |
| 流式 chunk 更新 | `appendShellChunk(runId, chunk)`：O(1) 字典写入，只重渲染订阅该 runId 的卡片                            | `streamUpdate()` 改 `history[i].output`，immer clone 数组+消息对象，selector 全跑 | **Kiro**（长会话放大） |
| 会话加载/切换   | `getSessionHistory` 拉事件流 → `filter(isRenderable)` → `prependToSession` 重建 turns 树，O(历史消息数) | history 本身即持久化结构，反序列化直接渲染                                        | **Continue**           |
| 老会话工具卡    | 从历史 `tool_call` + `tool_call_update` 静态渲染，无实时态                                              | markdown 重写器生成静态卡片                                                       | 等价                   |

- **运行期流畅度**：Kiro 更好（这正是卡片抖动的根源）
- **加载期**：Continue 更好
- 日常短会话感知差距不大

## 3. 老会话加载：Kiro 不重放事件流（已验证，纠正早期猜测）

早期猜测「Kiro 要重放事件到切片才能重建卡片」——**错误**。实际链路：

```js
// useLoadMoreHistory
const h = await e("getSessionHistory", { sessionId, beforeMessageId });
const p = h.updates.filter(kN); // kN = isRenderableSessionUpdate
u(p); // prependToSession
```

`kN`（`isRenderableSessionUpdate`）只保留 6 类事件：

```js
new Set([
  "user_message_chunk",
  "agent_message_chunk",
  "agent_thought_chunk",
  "tool_call",
  "tool_call_update",
  "session_info_update",
]);
```

- `prependToSession` 转成 `completedTurns` 树（`gq(r)` + `Bi()`），**不写回** `streamedShellOutput` / `userInputAnswers`
- `switchSession` 时运行时切片被显式重置为空（`yb` / `U5` 常量）
- 所以老会话工具卡是**静态最终结果**：显示输出，但不实时流式、不可再点 Submit（答案已在历史里）

Kiro 敢用纯切片模式的前提：**切片不持久化，老会话用静态渲染兜底**。Continue 的 history 持久化反而是优势——老会话天然完整，不需要事件流重建。

---

## 4. 我们的现状（My-Agent-editor/continue）

已完成的结构化改造（把 Kiro 的单一协议思想落地到 Continue 架构）：

- `user_input` / MCP 工具：emit native `toolCall` + 同 id `toolResult`，`toolCallState` 就地更新 → 无抖动
- `execute_pwsh` 实时输出：已走 `executeProgressStore[runId]` 独立切片（= Kiro 的 `streamedShellOutput` 模式）
- 老会话：`rewriteDeepAgentToolBlocks` 生成静态卡片（= Kiro 的历史静态渲染）
- 工具定义：以 DeepAgent 为唯一权威，`toolView` 投影给 GUI；MCP 配置保留在 Continue

**结论**：我们已是「history 持久化 + runId 切片做高频输出」的混合模式，拿到了 Kiro 模式的核心收益，不需要重构整个状态层。

## 5. 待决策：是否全盘改造成 Kiro 模式

### 优点（若改造）

1. 运行期增量更新，长会话流式更流畅
2. 新增工具不改 switch：按交互模式归到已有切片
3. 状态与展示解耦，多会话按 sessionId 隔离更干净

### 缺点（若改造）

1. 与现有 `toolCallState` 形成**双状态源**（卡片从哪读？切换点在哪？）
2. 历史回放要写「从 history 回填切片」的逻辑，否则老会话无中间态
3. Continue 原生工具 + MCP App UI 仍走 `tools/call`，要么双轨渲染（与收敛目标矛盾），要么连 core 一起改
4. 调试复杂度上升（`toolCallId` + `sessionId` 嵌套 key + `_meta.kiro` 元数据）

### 触发条件（什么情况下才值得改）

- 出现**多个**需要高频流式/增量状态的交互工具（目前只有 `execute_pwsh` 一个）
- 或长会话（>50 条消息）+ 高频 chunk 时出现可感知卡顿

### 当前决定

**暂不改造。** 先把 `execute_pwsh` 的 native 化做完（最后一处两阶段抖动），观察实际体验。若后续出现上述触发条件，再单独立项按 Kiro 切片模式重构。

## 6. Kiro 不同工具的卡片输出（outcome-summary）—— 已落地对齐

> [!info] 数据来源（确凿）
> `mermaid-GHXKKRXX-BPr5O2SG.js` 中 `bk` 组件内的 `getToolCall(w)` 分发函数（`a(...,"getToolCall")`）。

### 6.1 Kiro 卡片分发：不是 `HostCapabilitiesProvider`，而是 `getToolCall`

`HostCapabilitiesProvider` 只是事件 dispatcher。真正的「工具 → 卡片组件」映射在 `getToolCall`，优先级从上到下（先命中先返回）：

| 优先级 | 判定条件                                                                    | 卡片组件                                            | 变量                                     |
| ------ | --------------------------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| 1      | `isPowersUseToolCall`（title = `@power/server/tool` + rawInput.action=use） | PowersToolCall                                      | `wS`                                     |
| 2      | `_meta.kiro.serverName` 存在                                                | MCPToolCall                                         | `B0e`                                    |
| 3      | `_meta.kiro.toolId === "disclose_context"`                                  | DiscloseContextToolCall                             | `hpe`                                    |
| 4      | `_meta.kiro.toolId === "get_process_output"`                                | CommandToolCall                                     | `lS`                                     |
| 5      | `gpe(title)`（browser 类）                                                  | BrowserToolCall                                     | `xpe`                                    |
| 6      | `_meta.kiro.toolId === "user_input"`                                        | UserInputToolCall                                   | `kpe`                                    |
| 7      | `title === rO`（todo list）                                                 | TodoListToolCall                                    | `eme`                                    |
| 8      | `title === oy`（powers）                                                    | PowersToolCall                                      | `wS`                                     |
| 9      | `Epe(title)`（web search）                                                  | WebSearchToolCall                                   | `Npe`                                    |
| 10     | `Zfe(title)`（workflow）                                                    | WorkflowToolCall                                    | `tO`                                     |
| 11     | `kind` = delete/edit/execute/fetch/move/read/search                         | Delete/Edit/Command/Fetch/Move/Read/Search ToolCall | `npe`/`L0e`/`lS`/`ope`/`spe`/`l0e`/`tpe` |
| 12     | `_meta.kiro.kind === "agent-subtask"`                                       | SubtaskToolCall                                     | `Z0e`                                    |
| 13     | `_meta.kiro.kind === "analyze-requirements"`                                | AnalyzeRequirementsToolCall                         | `ape`                                    |
| 14     | 兜底（其余全部）                                                            | **DefaultToolCall**                                 | `epe`                                    |

> [!tip] 解释「为什么有的卡片只有工具名」
> 卡片结构统一是 `Je.Summary`（必有）+ `Je.Details`（可选）。`DefaultToolCall` 只渲染 `status icon + tool-call-title`（Details 仅在有 `locations` 时出现），所以看起来「只有一个工具名」；`ReadToolCall`/`CommandToolCall`/`EditToolCall` 等则在 Details 里塞文件内容、命令输出、diff，所以「有详情」。**差异来自各卡片组件自己决定 Details 渲染什么，而不是统一 summary**。

### 6.2 Kiro 各卡片的 Summary / Details 内容

| 卡片              | Summary                                                                | Details                                         |
| ----------------- | ---------------------------------------------------------------------- | ----------------------------------------------- |
| ReadToolCall      | eye icon + title + `tool-call-locations`（可点 file-label）            | 无                                              |
| CommandToolCall   | terminal icon + title + `kiro-command-cwd`                             | `kiro-command-text`（命令）+ Divider + 终端输出 |
| EditToolCall      | edit icon + (reverted) + title + locations + Actions(View diff/Revert) | inline diff（oldText/newText）                  |
| DeleteToolCall    | diffRemoved icon + title + locations                                   | 无（Summary-only）                              |
| MoveToolCall      | diffRenamed icon + title + sourcePath + → + dest file-label            | 无（Summary-only）                              |
| FetchToolCall     | globe icon + title                                                     | URL 链接 / domain                               |
| SearchToolCall    | search icon + title                                                    | explanation / why 文本                          |
| UserInputToolCall | question icon + title（问题文本，markdown 渲染）                       | `user-input-answer`（答案）                     |
| WebSearchToolCall | globe icon + title + `N results` + Expand 按钮                         | 结果列表（展开时）                              |
| TodoListToolCall  | checklist icon + title + `u/c` 进度                                    | todo 列表 + 修改文件                            |
| MCPToolCall       | status icon + title + Show Logs/Debug 按钮                             | `kiro-mcp-input` + Divider + `kiro-mcp-output`  |
| SubtaskToolCall   | eye icon + title                                                       | 子任务的 message/tool_call 列表                 |
| DefaultToolCall   | status icon + title                                                    | locations（可选）                               |

共同规律：

1. **Summary 必有**：status icon（codicon 语义：eye/terminal/edit/search/globe/question/...）+ `.tool-call-title`（短标题）。
2. **Details 按需**：只有工具真的产出了可展示内容（diff/输出/答案/列表）时才渲染。
3. state → icon 语义色：accepted(绿)/pending(琥珀)/rejected(红)/running(蓝)。
4. 折叠：外层工具组 `collapsible-container`，单个卡片内部 Summary 点开 Details。

### 6.4 全部工具统一到 native toolCall + case 映射（2026-11-25 续）

上一节做完后用户确认「其它工具也在 case 里加上，统一处理」。于是把 emit 路径和路由一并统一：

**emit 侧**（`DeepAgentLLM.ts`）：`structured` 从「只有 user_input / MCP / execute_pwsh / spec 工具」改为**恒 true**。所有 DeepAgent 工具都发 native `toolCall` + 同 id `toolResult`，id = `deepagent-${name}-${call.id}`。老会话的持久化 markdown 历史不动，仍由 `rewriteDeepAgentToolBlocks` 静态渲染。

**GUI 侧**：

- `FunctionSpecificToolCallDiv` 的 `switch` 保留专用 case（`read_file`/`read_files` → ReadFile，`execute_pwsh` → ExecutePwshCard，`user_input` → UserInputCard，spec 工具 → SpecWorkflowCard），`default` 从 `return null` 改为 `<GenericToolCallCard>` —— 覆盖剩余全部工具（fs*write / fs_append / str_replace / delete_file / file_search / grep_search / list_directory / web*_ / 3 个 DAG task / invoke_sub_agent / 4 个 Kiro extra / mcp\_\__）。
- 新建 `SpecWorkflowCard.tsx`：Kiro DefaultToolCall 风格（rocket icon + 短标题 + reason badge + 可折叠 result）。
- 新建 `GenericToolCallCard.tsx`：Kiro DefaultToolCall 骨架 + 两个补强 —— ① 从 `path`/`paths`/`targetFile`/`tasksFilePath` 提取并渲染可点击 file-label；② 结果含 `--- a/` 时渲染 inline diff + View diff 按钮。这样写类工具也有 EditToolCall 的观感。
- `ToolCallDiv/index.tsx`：id 带 `deepagent-` 前缀的卡片跳过 `ToolCallDisplay` 包裹（避免状态图标和标题双重显示），直接渲染 `FunctionSpecificToolCallDiv`。

**收益**：所有新会话工具卡都进同一个 `collapsible-container` 折叠组（运行中展开、完成折叠），Kiro 的 toolCallUpdate 语义（同 id 就地更新）覆盖全部工具；不再有工具落 `default: null` 变成空白行。

**待改进**：markdown 路径的 ReadOutcomeCard 等仍是独立卡片、不折叠（老会话/流式兼容路径）。若要连它也折叠，需在 `rewriteDeepAgentToolBlocks` / `StyledMarkdownPreview` 层做分组包裹，与新会话的 native 路径是两件事。

验证：改动文件 `read_lints` 0 error。
